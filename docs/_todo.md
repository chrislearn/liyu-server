# LiYu 服务端与客户端落地清单

更新：2026-09-26。依据 `OctoSense/liyu/docs/01–05`、`apps/liyu/src/data.rs`、`apps/liyu/src/lib.rs` 和当前 `liyu-server`。本文件是实施清单；`[ ]` 尚未完成，`[x]` 已有可验证实现。先完成领域 API 和隐私测试，再让在线 app 用这些 API；不能把现有单用户 `PUT /api/v1/state` 当作多人协作的最终协议。

## 0. 现状与必须先纠正的边界

- [x] 现有服务有 Salvo、Diesel、PgSQL、迁移、测试账号、基础登录、33 件演示商品和整份状态读写；客户端在连接失败时能回退本地演示。
- [x] **P0：默认停用整份状态 `GET/PUT /api/v1/state`。** 仅 `LIYU_ENABLE_LEGACY_STATE=1` 可在隔离的旧演示中临时开启。`PersistedState` 混存送出/收到礼物、谜底、称呼、地址、券码、好友心愿单和本机通讯录，不能作为多人在线协议。
- [ ] **P0：客户端移除整包同步及服务器删掉旧写入口。** 当前客户端仍会尝试旧路径，收到 410 后回退本地；需要逐页接领域 API 才能完成这项。
- [ ] **P0：统一身份与关系。** `user_id` 为不可变主键，手机号和邮箱是可修改、可验证的登录别名；熟人关系是双方确认的关系，不能靠备注姓名授权。未建立关系的人不得看心愿单或送礼。
- [ ] **P0：所有钱、订单、心愿认领、礼物状态在服务端事务内计算。** 前端传商品 ID、谜题和选择，不传最终价格、余额或状态。价格以订单快照保存；重复请求使用 `Idempotency-Key`。
- [ ] **P0：更新旧产品规则。** `OctoSense/liyu/docs/02-flows.md` 与送出详情当前会告诉送礼人“TA 换了一份/折成余额”；按这次需求，在线模式只给中性的“TA 已处理礼物”和原配送的签收/本人确认状态，不能暴露处理分支。离线演示旧文案也应同步调整。
- [ ] **P0：定下在线/离线切换规则。** 离线演示数据放独立命名空间并醒目标识，不在恢复连接后自动上传为真实交易；登录账户的离线草稿可保留本机，服务端冲突需提示用户。

## 1. 页面与 API 对照

表中 `已有 UI` 指当前桌面 liyu：挑礼、单件送礼/结算、礼盒/解谜/收下/换购/折现、契约、熟人、心愿单、钱包、设置。`需加 UI` 指这次需求新增；不要将 REST 完成误写为客户端已接入。所有端点前缀为 `/api/v1`；除注册、登录、公开商品外均需会话。

| 模块 / 前端动作 | REST API（请求/响应关键点） | 现状 / UI 工作 |
| --- | --- | --- |
| 注册、登录、登出、会话续期 | `POST /auth/register`, `/auth/login`, `/auth/logout`, `/auth/refresh`, `GET /me` | 注册/登录 API 初版已有；需加 app 内账户页、切换账户和过期处理。测试阶段密码与注册验证码均 `123456`，不发送邮件短信；以后改真实认证。 |
| 个人资料 | `GET/PATCH /me/profile`（display_name、avatar_url 白名单）；`PUT /me/phone`, `PUT /me/email`（测试码）；后续 `PUT /me/password` | 显示名、手机、邮箱 API 已有；当前只可改本地 `settings.nickname`，需加资料页和登录/密码表单。手机号/邮箱不得出现在公开资料。 |
| 头像 | 目前 `PATCH /me/profile` 仅接受受约束 HTTPS `avatar_url`；目标 `POST /me/avatar`（限定 JPEG/PNG/WebP、大小/尺寸、裁切），`DELETE /me/avatar`；`GET /media/avatars/{id}` | URL 引用不是实际上传；需加头像选择/预览/上传与默认头像，数据库只存媒体 ID。 |
| 收货地址 | `GET/POST /me/addresses`, `PUT/DELETE /me/addresses/{id}` | 服务端 owner-only CRUD 已有；当前前端只在收礼时录入上次收件信息，需加地址簿 UI。送礼人不能读取。 |
| 通知偏好 | `GET/PATCH /me/settings` | UI 已有三个提醒开关和主题；本地偏好与服务端通知偏好分开。 |
| 商品分类、搜索、详情 | `GET /catalog/categories`, `GET /catalog?category=&q=&cursor=`, `GET /catalog/{id}` | 服务端已对齐 33 件与字段；挑礼/商品详情 UI 仍读代码常量，需切 API。 |
| 商品图 | `GET /media/products/{product_id}/{variant}`（thumb/card/detail） | 已有 33 张本地图；补真实感演示图、来源/许可记录、压缩尺寸及服务端静态资源；离线复用打包图。 |
| 购物车 | `GET/DELETE /cart`, `POST /cart/items`, `DELETE /cart/items/{id}` 已有；目标再加 `PATCH /cart/items/{id}` | **需加购物车页/角标/加购/移除/结算。** 当前每行只记录商品+收礼人，谜题/契约配置尚未接入。 |
| 报价、下单、测试支付 | `POST /orders/quote`, `POST /orders`（幂等键）, `GET /orders`, `GET /orders/{id}`, `POST /orders/{id}/pay-test` 已有；目标再加礼物玩法/预约日/心愿认领/钱包流水与取消 | 当前服务端按商品快照价格在事务内下单、测试支付创建礼物；尚无钱包扣减及前端购物车页，不能称为完整业务结算。 |
| 心愿单 | `GET/POST /wishlists`, `GET/PATCH/DELETE /wishlists/{id}`, `POST /wishlists/{id}/close`, `GET /contacts/{id}/wishlists` | 发布、编辑、结束、删除 UI 已有；在线改为按 owner 和 audience 检查，已认领条目不可移除。认领与订单创建同事务，避免撞礼。收礼人仅看“已有人送”，揭晓前不看赠送者或替代款。 |
| 熟人 | `GET /contacts`, `POST /contacts/invitations`, `POST /contacts/invitations/{id}/accept`, `DELETE /contacts/{id}` | 当前“熟人”仅本机称呼/vCard；需增加邀请/接受/拒绝 UI，联系人导入只在本机匹配，不上传整本通讯录。 |
| 礼盒 / 神秘礼 | `GET /gifts/inbox`, `/gifts/outbox`, `GET /gifts/{id}`, `POST /gifts/{id}/open`, `/answer`, `/accept`, `/exchange`, `/cash-out`, `/withdraw` | 页面和本地规则已有；需让服务端执行业务状态机，答题次数、揭晓身份、7 天过期、券码发放与一次性领取不可由客户端伪造。入/出站使用不同响应 DTO。 |
| 物流和确认收货 | `GET /shipments/{gift_id}`, `POST /shipments/{gift_id}/confirm-receipt`（仅收礼人）；`GET /gifts/{gift_id}/delivery-summary`（仅送礼人） | 三个服务端端点和投影已实现并通过三账号联调。**需加客户端物流页及测试物流推进器**；送礼人只见签收/确认布尔值，物流签收与本人确认分开。 |
| 契约 | `GET /pacts`, `POST /pacts/{id}/fulfil`, `/waive`, `/nudge` | UI 已有；仅当事人操作，提醒限频，契约状态和礼物状态事务联动。 |
| 钱包 | `GET /wallet`, `GET /wallet/ledger?cursor=`, `POST /wallet/top-up-test` | 现有钱包/流水 UI；演示充值只在开发模式可用。所有余额由服务端流水求和或受约束余额表产生，不能由 `state` 上传。 |
| 通知 | `GET /notifications`, `POST /notifications/{id}/read` | 当前本地计算到期提醒；在线由服务端基于礼物、心愿和契约生成，不泄露发送者或隐藏商品。 |
| AI | 延续本机 AI bus 的 `list_gift_catalog`、`suggest_gift`、`get_gift_box_summary`，只读 | AI 不获得状态写 API 或管理员物流接口；若将来开放购买/收礼，须明确工具风险、逐次用户确认及服务端授权。 |

## 2. 数据库与协议设计

- [ ] **P0** 新迁移：`users`（display_name、password_hash）、`user_contacts`（phone/email 正规化、验证时间、唯一索引）、`sessions`（哈希 token、到期/撤销）、`media`、`addresses`、`friendships`/`invitations`。现在固定密码只是测试 fixture；禁止把 token、地址、手机号、邮箱写日志。
- [ ] **P0** `products`、`product_images`、`categories`：与前端 33 个商品 ID 对齐，价格分整数、品牌、规格、详情、库存/可售、排序和素材授权。价格和图更新不改历史订单。
- [ ] **P0** `carts`/`cart_items`、`orders`/`order_items`、`payments_test`、`wallet_entries`。订单行锁、幂等键、金额校验、重复支付/取消测试。
- [ ] **P0** `wishlists`/`wishlist_items`/`wishlist_audience`、`gifts`/`gift_attempts`、`pacts`、`voucher_issues`。关系 ID 而非姓名；私密答案在服务端保存，响应永不返回。认领用唯一约束 + 事务。
- [ ] **P0** `shipments`/`shipment_events`（承运商、单号、收件快照、发货/揽收/运输/派送/签收）、`receipt_confirmations`。换购生成**收礼人私有的后续履约单**；原送礼订单只投影初始礼物的发货/签收/确认状态，不关联后续商品或余额去向。
- [ ] **P1** 响应采用显式 DTO，绝不直接 `Serialize` 数据库实体；列表游标分页、统一错误码和字段错误；OpenAPI 文档与示例请求。服务器时间使用 UTC，前端只负责显示。
- [ ] **P1** 领域事件/事务后通知；演示物流推进器可以定时或按钮触发，但只在 `LIYU_DEMO_MODE=true` 且受保护的管理入口可调用，普通用户无权编造签收。
- [ ] **P1** 对所有 `POST` 状态转换加入幂等与乐观/行锁控制，尤其同时认领同一心愿、重复猜题、双击付款、重复确认收货。

## 3. 隐私响应矩阵（以服务器代码和集成测试强制）

| 信息 / 阶段 | 收礼人 | 送礼人 | 其他熟人 / AI |
| --- | --- | --- | --- |
| 未揭晓的礼物、心愿认领 | 仅玩法/线索和“已被认领”，不含送礼人、谜底、具体替代商品 | 可看自己购买的原商品、订单价和自己设置的玩法 | 心愿项只显示“已有人送”；AI 不看心愿单 |
| 揭晓后身份 | 仅满足解谜/契约规则后可见 | 自己的信息 | 不能经列表或通知推断 |
| 收货地址、电话、姓名、运单号及完整物流 | 本人可看自己的履约单 | **全部不可见** | 全部不可见 |
| 原礼物配送 | 完整状态/时间线；本人可确认收货 | **只看是否物流签收、本人是否确认收货**；可显示发货布尔态 | 不可见 |
| 收礼后换购/折现、差价、券码、后续物流 | 仅收礼人 | **不可见；原单送达摘要不随换购暴露额外细节** | 不可见 |
| 钱包、账户联系方式、私密答案 | 仅本人/服务端必要逻辑 | 不可见 | 不可见，AI 仅聚合计数 |

- [ ] **P0** 双用户/第三用户的 API 黑盒测试：交换 token、猜 ID、列表与单件查询、错误响应、分页、通知和 AI 输出均不得泄露禁止字段。
- [ ] **P0** 测试“送礼人观察差异”：收礼人换购、折现、改地址、领取券码后，送礼人的 `delivery-summary` 响应保持相同（除原物流签收与确认布尔态）。
- [ ] **P0** 移除现有 `/state` 对在线用户的写能力前，不能宣称上述隐私矩阵已落实。
